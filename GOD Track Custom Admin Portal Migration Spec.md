# GOD Track: Custom Admin Portal Migration Spec

- ### Sep 26, 2026 · @Nicholas Gyamfi

This document is for the team building the admin portal inside your mobile app. It describes exactly what GOD Track (the WordPress plugin currently used by GOD staff and admins) does today, page by page, so the mobile team can rebuild or absorb the same functionality into their own custom backend without inventing anything new or leaving anything out.

It also covers the integration question directly: once the mobile team's custom backend becomes the place where staff create and manage opportunities, programs, partners, and ambassadors, how does that data still show up live on the public GOD website, which runs on WordPress. The short answer is that WordPress stops being where staff work and becomes a display layer only, fed by a set of new API endpoints described in Section 5. Staff log into the custom backend, publish there, and it appears on the website automatically.

This document is split by role. Read Section 1 together as a team first, since it sets up concepts every role depends on. After that, your frontend developer should work from Section 2, your backend developer from Section 3, and whoever owns layout and screen design from Section 4. Section 5 ties it together as a step-by-step plan.

Everything below is organized by who does the work, not by page. Section 2 is written for the frontend developer, Section 3 for the backend developer, Section 4 for whoever owns UI and UX, and Section 5 is the shared step-by-step plan. Each section repeats the concepts it needs, so any one of them can be handed to that person on its own.

1. Quick orientation

## 2. For the frontend developer: screens to build

Build each of these as its own screen in the app's existing design system, not a bolted-on module. Five things worth knowing before you start: Opportunities are external listings anyone can apply to, gated by vetting. Programs are GOD's own internally run activities, a completely separate table from Opportunities. Partners are organizations moving through a six-stage pipeline. Ambassadors amplify existing public listings using a referral code, they do not own content. Database records are the beneficiaries themselves, tagged organic or referral so ambassador impact is traceable. Keep those five separate in your data model exactly as separate, mixing any two will make every screen below behave wrong. For every screen, the fields listed are exactly what the form or table needs, no more, no less. Every save action calls the matching backend endpoint described in Section 3; do not write directly to MongoDB from the frontend for anything that also needs to appear on the public GOD website, since only the backend's write-through to WordPress makes that happen. Access is role-based: a user typically holds one or two of Partnerships Officer, Opportunities Officer or Writer, Training and Capacity Development Officer, Database Officer, Communications Officer, Social Media Manager, Country Lead, Admin Support, or Desk Lead, and each screen should only be reachable or editable by the roles that own it, gate navigation and edit actions on that, not just on being logged in.

**Dashboard.** Ten KPI cards, each showing a value, a target, a unit, a status color of green amber or red, and a short explanatory note. Below that: a trend chart, a priorities panel with progress bars toward each monthly target, an upcoming-programs table, and a recent-activity feed. Every number on this screen is fetched from the backend, never typed in or cached client-side longer than a refresh cycle, since these are live figures.

**Opportunities.** A list view with filters for country, type, and status, plus a create/edit form. Form fields: title, description, offering organization, organization logo upload, application deadline, official application link, cost or fee label, format (online, in-person, hybrid), free-text location, country selector, optional event date and time, duration label, opportunity type, featured image, assigned writer. Include a toggle labeled referral code on apply. Include a vetting section: a checkbox for vetted, who vetted it, and when. The publish action must be disabled in the UI until vetted is checked, matching the gate the backend also enforces. Each opportunity's detail view should show total views and total applications, each with a website versus app breakdown underneath, so staff see the combined figure at a glance and can still tell which channel it's coming from.

**Programs.** List and form, separate from Opportunities. Fields: title, program type (training, bootcamp, webinar, outreach, project, mentorship, event), status (planned, running, delivered, cancelled), format, optional linked partner, country, location, current participant count, participant target, facilitators, notes, start date and time, end date and time. Show active count (planned plus running) and delivered count as two separate figures anywhere programs are summarized.

**Partners.** A pipeline board with six columns: prospect, outreach, proposal, MOU, onboard, renew. Card fields: organization name, partner type (corporate, university, foundation, NGO, government, media and tech), assigned owner, country, contact name, contact email, contact phone, what they provide, how sourced, notes. Moving a card into onboard or renew should set a closed flag automatically, do not add a separate manual toggle for that. Include a pipeline health indicator fed by the backend's calculation, described in Section 3.

**Network (Ambassadors).** Directory and form. Fields: full name, email, phone, country, city, profile photo, member type, description, role title, campus, tier (Ambassador, Senior Ambassador, Campus or Regional Lead), status (applicant, onboarding, active, dormant), assigned lead, trained flag, linked user account if applicable. Referral code is generated by the backend on creation, do not add an input for it, display it read-only. Include a log-amplification action: channel used and an optional note, tied to the ambassador record.

**Leaderboard.** Read-only ranked table for a selected month: rank, name, country, campus, tier, shares logged, distinct referred clicks, verified signups attributed. No edit actions on this screen at all.

**Database.** Beneficiary records table. Fields: full name, email, phone, country, institution, source type (organic, ambassador referral, event, partner channel, bulk import), linked ambassador if referral, linked opportunity if relevant, verified flag, added-by and added-on. Filters for source and verification status. A one-click verify action on pending records. Show a monthly pace gauge against the target, fed by the backend, not computed client-side.

**Social.** Manual log form and monthly totals view. Fields: platform (Facebook, Instagram, X, LinkedIn, TikTok, YouTube, WhatsApp, other), post title, post URL, reach, engagement, optional linked opportunity, date posted. Totals broken down both team-wide and per platform for the current month. No live API pull from social platforms, this stays manual entry.

**Team and My Scorecard.** Team is oversight-only: every staff member, role, and a composite score zero to one hundred for a selected month, plus each person's strongest and weakest metric. My Scorecard is the same view scoped to whoever is logged in, with no visibility into colleagues' scores. Build these as two screens sharing one component, gated by role.

**Monthly Report.** A generated, downloadable report view for a selected month: the ten KPIs with status, partner pipeline health, database pace, records-by-source breakdown, ambassador network size and activity rate, top five ambassadors, social totals, full team scoreboard. Build a second, separate partner-facing version that excludes every individual staff figure, no names, no per-officer scoring, showing only aggregate reach and month-over-month growth.

**Testimonials.** Moderation queue: name, email (never displayed, staff-only), comments, optional photo, with approve, unpublish, and reject actions. Approved items feed the public testimonials page via the backend.

**Settings.** Monthly targets per KPI, pipeline stage labels, integration credentials, and a personal account page per user. Treat integration credentials as write-only in the UI, never render a saved API key back out in full.

## 3. For the backend developer: what to build

Your MongoDB collections are the system of record going forward. Staff create and edit everything against your API, backed by MongoDB, same as any other part of the app. Keep five entities distinct in your schema: Opportunities are public listings gated by a vetting flag, Programs are GOD's own internally run activities and a separate collection entirely, Partners move through a six-stage pipeline, Ambassadors amplify existing listings via referral code rather than owning content, and Database records are the beneficiaries, each tagged organic or referral. The one thing that makes this different from a normal CRUD API: every write to Opportunities, Programs, Partners, Ambassadors, Database records, and Social posts also has to push a copy to WordPress, so it shows up on the public GOD website. WordPress becomes a display mirror, fed by you, never edited directly again.

**The pattern for every write endpoint below is the same three-step sequence.** One, validate and save to MongoDB as you normally would. Two, call the matching new WordPress endpoint over HTTPS, sending the record's fields plus your stored WordPress API credential. Three, take the WordPress post ID or row ID that comes back in the response, and store it on your MongoDB document, for example as a field called wordpress\_id. Every future edit or delete of that record sends the same wordpress\_id back to WordPress so it knows which existing item to update rather than creating a duplicate.

**Credential handling.** Generate one WordPress application password or API key, and store it only in your backend's own server environment as a secret, never in the mobile app, never in a client-accessible config. Every one of your calls to WordPress includes it. If a WordPress call fails, for example the site is briefly down, do not fail the whole save, since the record must still exist in MongoDB, but do flag that document as not yet synced and retry, so a WordPress outage never blocks staff from working.

**Six endpoints to call, one per record type.**

Create or update opportunity: send it every time an opportunity is saved. Before sending, check your own vetted field is true, since WordPress will also enforce this and reject an unvetted publish, but checking on your side first gives a cleaner error back to the frontend. Required fields to send: title, description, organization, deadline, application link, format, location, country, opportunity type, vetted status, vetted by, vetted date. Optional: logo, cost label, event date and time, duration, featured image, assigned writer, referral-code-on-apply flag. Separately, every time someone views an opportunity or applies to one, log that event tagged with its source, website or app, rather than as one anonymous count. Total views and total applications are then just the sum across both sources, with the per-source breakdown always available underneath, so the dashboard and reports in Section 2 can show both without a second tracking system.

Create or update program: send status as one of planned, running, delivered, cancelled, exactly those strings, since delivered is the only one WordPress counts toward the monthly target. Send title, program type, status, format, country, location, participant count, participant target, facilitators, notes, start and end date-time, and the linked partner id if one exists.

Create or update partner: send the pipeline stage as one of prospect, outreach, proposal, MOU, onboard, renew. When the stage is onboard or renew, do not send a separate closed flag, WordPress sets that automatically from the stage, same as your own MongoDB logic should. Send organization name, partner type, owner, country, contact name, contact email, contact phone, what they provide, source, notes.

Create or update ambassador: on first creation only, do not generate the referral code yourself, let WordPress generate it and return it in the response, then store that returned code on your MongoDB document as the single source of truth for it going forward. Send full name, email, phone, country, city, member type, description, role title, campus, tier, status, assigned lead, trained flag.

Add database record: WordPress deduplicates by email first, then phone, before creating a new entry. If your own MongoDB layer also dedups, use the same order, email first, so the two systems never disagree about whether a record is new. Send full name, email, phone, country, institution, source type, linked ambassador id if referral, linked opportunity id if relevant.

Log social post: the simplest of the six, minimal validation. Send platform, post title, post URL, reach, engagement, date posted, and optional linked opportunity id.

**Computed figures your own API needs to replicate, not just proxy.** The dashboard KPIs, the partner pipeline health gauge, the database monthly pace, and the team and individual scorecards are not raw counts, they are targets compared against live totals with a green, amber, red status. For the partner pipeline specifically, the calculation is forward-looking: given the historical close rate, how many open deals are needed right now to hit next month's target, and is the current open pipeline thin against that. For the Team and My Scorecard screens, the composite score per person is an average attainment across only the metrics that person's own role owns, capped so one strong metric can't hide a neglected one, do not average across metrics outside their role. Pull the actual target values and thresholds from WordPress settings rather than hardcoding them on your side, since Section 2's Settings screen is where staff will change them, and if your backend has its own hardcoded copy the two will drift apart the first time someone updates a target.

**Authentication on the WordPress side.** These six endpoints must reject any request without a valid credential, returning an authentication error, and must never be reachable without one, unlike the existing read-only endpoints at slash wp-json slash god slash v1 slash, which stay public and unchanged since they already serve the app's public-facing opportunity feed, leaderboard, and KPIs.

This is mechanical, well-scoped work, and Claude or Claude Code can build the WordPress side of it directly against the real GOD Track plugin files. Test each endpoint in isolation with a basic request before wiring up the real integration end to end.

## 4. For UI/UX: layout and design guidance

Do not design these screens from scratch against a blank page, and do not simply copy the WordPress admin's look. Use the field lists in Section 2 as the fixed content each screen must hold, then lay it out in the app's existing design language so it reads as one product, not a bolted-on admin panel. Keep in mind the five entities behind these screens are genuinely separate: Opportunities are public listings gated by vetting, Programs are GOD's own internally run activities, Partners move through a six-stage pipeline, Ambassadors amplify listings via referral code, and Database records are the beneficiaries themselves. Screens for these should never visually imply they are variations of the same list, since staff read them as different tools for different jobs. Access is role-based too, for example a Partnerships Officer and a Database Officer, so design navigation that only surfaces the screens a given role actually owns, rather than one flat menu everyone sees in full.

**Dashboard first, since it sets the visual language for everything else.** Ten KPI cards in a grid, each card showing the value large, the target and unit small beneath it, and a color-coded status, green amber or red, as a border, dot, or background tint rather than a colored block that fights the app's palette. Below the cards: a trend chart, a priorities section using progress bars against each target, an upcoming-programs list, and a recent-activity feed, in that reading order top to bottom, since that mirrors how staff will actually scan it each morning.

**List and pipeline screens share one pattern.** Opportunities, Programs, Database, and Social are all filterable tables or lists feeding into a detail or edit form. Design one reusable list component with a filter bar and a consistent row layout, then reuse it across all four rather than designing each separately, that consistency is what will make the portal feel coherent rather than assembled from four different tools. Partners is the one exception, it is a kanban-style pipeline board with six columns, prospect through renew, and needs drag-or-tap-to-advance interaction rather than a table.

**Forms should group fields the way staff think about them, not the way they're stored.** For Opportunities, for example, group basic details, then logistics like format and dates, then the vetting block, separately and visually distinct, since vetting is a gate, not just another field, it should look like a checkpoint. For Ambassadors, keep the referral code visible but clearly read-only, greyed or locked-looking, since staff should never try to type into it.

**Team and My Scorecard need a strength and weakness callout, not just a score.** A composite number alone doesn't tell a manager where to help, so design a small highlighted strongest-metric and weakest-metric pair on every card, that's the part of this screen that actually gets used day to day.

**Two report layouts, not one with a toggle.** The internal Monthly Report and the partner-facing version have different audiences and different content, the partner one must never risk leaking individual staff scores through a mis-set toggle, so treat them as two separate templates from the start rather than one screen with a show-or-hide switch.

If it would help to have a starting point rather than designing every one of these from nothing, a reference set of screens can be generated next, matching the field lists above, for your designer to restyle into the app's own visual system rather than laying out each screen's structure from a blank canvas. Say the word and that can be produced as a follow-up.

## 5. Step by step plan

First, read Sections 1 through 4 together as a team, frontend, backend, and design in the same room or call, so everyone agrees on the field lists and the split of responsibilities before anyone starts building. Second, the backend developer builds the six WordPress write endpoints from Section 3, one at a time, opportunities first, each one tested in isolation before moving to the next. Third, generate the WordPress API credential and store it in the backend's server environment only. Fourth, the frontend developer builds the screens from Section 2 against your own API, not against WordPress directly, while design finalizes layout per Section 4 in parallel. Fifth, test end to end with a small number of real records, create an opportunity through the new portal, confirm it appears correctly on the public GOD website, confirm the vetting gate holds, then repeat for programs and partners. Sixth, once confirmed working, retire staff access to the WordPress admin screens entirely, so the custom portal is the only place anyone logs in to do this work.
